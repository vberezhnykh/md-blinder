# OCR-движки: Tesseract, PP-OCRv5, DeepSeek-OCR

Эксперимент: заменяем ли мы Tesseract.js на что-то более современное, не ломая
главное свойство продукта — всё считается в браузере, документ никуда не
уходит.

## Что сделано

* PP-OCRv5 (детектор DB + распознаватель CTC) реализован на `onnxruntime-web` и
  подключён как альтернативный движок для сканов — `src/lib/ocr/ppocr/`.
* Движок выбирается в UI под дропзоной, запоминается в localStorage,
  разово переключается через `?ocr=ppocr`. По умолчанию остаётся Tesseract.
* Бенчмарк на синтетических «сканах» с метриками CER / WER / доля правильно
  прочитанных реквизитов.
* Харнесс для DeepSeek-OCR, который кладёт результаты в ту же таблицу.

## Результаты на синтетических фикстурах

Четыре страницы: чистый рендер, мелкий шрифт с шумом и наклоном, выцветший
скан и двуязычный договор в две колонки. Одна и та же машина, один и тот же
браузер, 4 ядра CPU, без GPU.

| движок    | CER  | WER  | реквизиты | мс/страница |
|-----------|------|------|-----------|-------------|
| tesseract | 1.1% | 1.9% | 31/31     | 1670        |
| ppocr     | 1.4% | 4.6% | 30/31     | 4590        |

По качеству движки практически сравнялись, Tesseract остаётся втрое быстрее.
Постранично: на чистой и выцветшей странице Tesseract безошибочен, на шумной
чуть лучше PP-OCR (CER 4.3% против 4.7%), на двуязычной чуть хуже (0.3%
против 0.0%).

Важная оговорка: фикстуры синтетические, то есть это ровно тот случай, в
котором Tesseract силён (чистый растр, прямые строки, стандартная гарнитура,
высокий контраст). Преимущество PP-OCR обычно проявляется там, где фикстур
пока нет: фотографии документов, JPEG-артефакты, печати поверх текста,
таблицы с линовкой, перекос страницы. На этом наборе разница между движками
в пределах шума, и менять движок по умолчанию не на чем; решать надо на
`test-samples/`.

Характер ошибок различается и это важнее среднего CER:

* Tesseract на шумной странице теряет символы в словах, но реквизиты читает.
* PP-OCR путает регистр (`НдС`, `СНилС`) и подменяет кириллицу латинскими
  омоглифами (`aдрес элeктpонной пoчты`, `A.Л.`). Для нас это опаснее опечатки:
  омоглиф проходит мимо регулярок и меняет токенизацию для NER.
* Ошибка PP-OCR в единственном потерянном реквизите — `1 480 000` прочитано как
  `1 480 о00`, то есть цифра заменена буквой. Ровно тот класс ошибок, ради
  которого в бенчмарке есть отдельная колонка «реквизиты».

## Как воспроизвести

```bash
npm install
node scripts/fetch-ppocr-models.mjs --bench   # веса PP-OCR + локальный Tesseract
node scripts/make-ocr-fixtures.mjs            # синтетические страницы
npm run dev                                   # в отдельном терминале
node scripts/bench-ocr.mjs --engines tesseract,ppocr
```

На своём корпусе:

```bash
node scripts/bench-ocr.mjs --dir test-samples/scans --engines tesseract,ppocr
```

Рядом с каждым `<name>.png` должен лежать `<name>.txt` с эталонным текстом.
Полезные ключи: `--det-limit 1536` (длинная сторона входа детектора; на мелком
шрифте иногда добирает пару реквизитов, на наших фикстурах CER не менял),
`--out файл.json`.

Сквозная проверка на «скане» целиком (страницы-картинки без текстового слоя):

```bash
node scripts/make-scan-pdf.mjs        # собирает PDF из фикстур
# дальше просто загрузить tests/local/ocr-fixtures/scan.pdf в приложение
```

## Веса и лицензии

`scripts/fetch-ppocr-models.mjs` кладёт в `public/models/` (каталог
в `.gitignore`, ~13 МБ):

| файл       | что это                             | размер |
|------------|-------------------------------------|--------|
| `det.onnx` | `PP-OCRv5_mobile_det`               | 4.7 МБ |
| `rec.onnx` | `eslav_PP-OCRv5_mobile_rec`         | 7.9 МБ |
| `dict.txt` | словарь 518 символов                | 2 КБ   |

Распознаватель именно `eslav` (восточнославянский): у базового PP-OCRv5 в
словаре **нет ни одной кириллической буквы**, он физически не может выдать
русский текст. Это первое, что стоит проверять при любой замене модели.

Двуязычные договоры при этом читаются одним проходом, без переключения языков:
в словаре `eslav` 76 кириллических символов и 115 латинских плюс цифры, «ёлочки»,
№, ₽ и ₴. Отдельной модели для английского не нужно. Обратная сторона того же
свойства — путаница омоглифов (латинская `a` вместо кириллической), см. выше.

Всё под Apache-2.0 (и код PaddleOCR, и веса моделей PP-OCR). ONNX-экспорт
берётся из зеркала `PT-Perkasa-Pilar-Utama/ppu-paddle-ocr-models`, потому что
официальные веса лежат в paddle-inference формате; при желании их можно
сконвертировать самим через `paddle2onnx` и подменить файлы.

`onnxruntime-web` версия зафиксирована ровно (`1.19.2`) — та же, что тянет
`gliner`. Разъезд версий даст в бандле две копии рантайма.

## Двуязычные договоры в две колонки

Договор с переводом свёрстан в две колонки, и оба движка читали его поперёк:
«ДОГОВОР ПОСТАВКИ SUPPLY AGREEMENT», предложения обрывались на середине,
NER работал по обрывкам. Правится в трёх местах конвейера, признак
«это перевод, а не таблица данных» общий — `src/lib/parallelTable.ts`:

* **docx** (`htmlToMarkdown.ts`) — двуязычная таблица разворачивается в
  последовательный текст: сначала одна языковая версия целиком, потом другая.
  Обычные таблицы (цены, спецификации) остаются таблицами.
* **текстовый PDF** (`pdfStructure.ts`) — на странице ищется вертикальный
  жёлоб между колонками, элементы делятся по нему, каждая колонка читается
  сверху вниз.
* **OCR** (`ocr/pageText.ts`) — то же самое по рамкам строк, общий код для
  обоих движков.

Опознаётся по алфавитам: колонка на кириллице напротив колонки на латинице,
обе с длинными кусками текста. Таблица «Наименование | Стоимость» под этот
признак не подходит и не трогается.

Отдельная тонкость для Tesseract: его собственный разбор считает строкой всю
ширину страницы, то есть русский пункт и перевод вместе, и рамка такой
«строки» перекрывает жёлоб. Поэтому у него берутся рамки **слов**, а не строк.

На двуязычной фикстуре это дало CER 78% -> 0.3% (Tesseract) и 68% -> 0.0%
(PP-OCR).

## Что понадобилось, чтобы PP-OCR заработал

Четыре ошибки, каждая из которых давала правдоподобный, но неверный результат —
записаны, чтобы не наступить второй раз:

1. **Ведущая пустая строка в `dict.txt`** — не пробел, а артефакт формата.
   Если считать её символом, весь алфавит съезжает на позицию: «Д» читается
   как «Ґ», пробел — как «я». CER 89%.
2. **Потолок ширины кропа строки.** Дефолт PaddleOCR (`320-480 px`) рассчитан
   на короткие китайские строки; строка договора на 1240 px сжималась втрое,
   символы сливались, половина текста пропадала. CER 60%. Ширина должна быть
   пропорциональна реальному соотношению сторон.
3. **Добивка узких кропов в пачке белым.** Кропы разной длины выравниваются
   по самому широкому в пачке, и хвост надо заполнять нулём — после
   нормализации `(x/255-0.5)/0.5` это нейтрально-серый, на нём модель
   обучалась. Заливка белым выглядит логичнее, но именно она превращала
   короткие строки в мусор («Kazan, the fifth day of May» -> «cYaananncnlob»),
   пока длинные в той же пачке читались верно. Самый коварный из четырёх:
   при батче в одну строку всё работало идеально.
4. **Чтение поперёк колонок** — см. предыдущий раздел.

## DeepSeek-OCR

Не запускался: это VLM на несколько миллиардов параметров, ей нужна
CUDA-видеокарта, и в браузер она не поедет ни в каком виде. Смысл прогона —
понять, есть ли у VLM-OCR запас по качеству на сложных сканах, ради которого
стоило бы заводить серверную часть (со всеми последствиями для приватности:
договоры с персональными данными в чужое облако отправлять нельзя, только
on-prem).

```bash
pip install torch transformers pillow accelerate
python scripts/deepseek-ocr/run.py --dir tests/local/ocr-fixtures --out deepseek-ocr.json
node scripts/score-ocr.mjs bench-ocr.json deepseek-ocr.json
```

Читать результат нужно иначе, чем у обычного OCR: VLM не распознаёт текст, а
генерирует его. Ошибка выглядит не как мусор в строке, а как правдоподобная
подмена — другая цифра в ИНН, другая фамилия, дорисованный пункт договора.
Поэтому смотреть в первую очередь на колонку «реквизиты», а не на CER, и
относиться к галлюцинации как к блокеру, а не как к «немного хуже качеству».

## Куда двигаться дальше

* Прогнать бенчмарк на реальных сканах из `test-samples/` — только это решает
  вопрос, других аргументов нет.
* Если PP-OCR выиграет на реальных данных: чинить омоглифы (постобработка по
  словарю или ограничение алфавита), включить `cls`-модель для страниц,
  перевёрнутых на 180°.
* Скорость PP-OCR упирается в wasm. Веб-версия `onnxruntime-web` умеет WebGPU
  (`executionProviders: ['webgpu']`) — на машинах с GPU это даст кратное
  ускорение; сейчас жёстко стоит `wasm`, чтобы результат не зависел от железа.
