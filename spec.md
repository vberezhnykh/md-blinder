# Техническое задание: браузерное приложение для конвертации документов в Markdown и анонимизации

Версия 2.0. Client-side архитектура (всё считается в браузере, без сервера).

## 1. Цель и общая идея

Приложение принимает юридические документы (договоры) в форматах `docx` и `pdf`, конвертирует их в Markdown и анонимизирует чувствительные данные. Пользователь получает чистый Markdown-текст без конфиденциальной информации, который затем можно безопасно загружать в облачные LLM (Claude, GPT и другие) — без риска раскрытия данных клиентов и без перерасхода токенов на разметку исходных форматов.

Приложение работает целиком в браузере. Документы не покидают компьютер пользователя.

Ключевая ценность:
- Markdown вместо `docx`/`pdf` — меньше токенов при загрузке в LLM.
- Анонимизация до отправки в облако — конфиденциальность договоров сохраняется.
- Обратимость — таблица замен позволяет восстановить оригинал.
- Приватность — данные не выходят из вкладки браузера.

## 2. Пользователь и сценарий

Пользователь — юрист, работает с англоязычными договорами. Проект личный, пользователь сам его контролирует. Русский язык и другие форматы добавляются позже.

Базовый сценарий:
1. Пользователь открывает приложение в браузере (обычная веб-страница по ссылке) и загружает файл (`docx`/`pdf`).
2. Браузер конвертирует файл в Markdown. Для PDF-сканов запускает OCR.
3. Приложение автоматически находит чувствительные сущности и предлагает замену.
4. Пользователь проверяет результат в редакторе: правит текст, добавляет или убирает сущности для анонимизации.
5. Пользователь экспортирует анонимизированный Markdown и таблицу замен.
6. При необходимости пользователь восстанавливает оригинальные данные по таблице замен (деанонимизация).
7. Обработанный документ остается в истории браузера, к нему можно вернуться.

## 3. Область (scope)

В первой версии:
- Форматы на вход: `docx`, `pdf` (текстовый и скан).
- Язык документов: английский.
- Выход: Markdown + таблица замен.

Вне первой версии (заложить архитектуру, но не реализовывать):
- Старый формат `.doc` (бинарный). В браузере он почти не конвертируется — нет надежной JS-библиотеки. Обходной путь для пользователя: открыть `.doc` в Word и сохранить как `.docx`. Нативную поддержку добавить позже.
- Русский и другие языки.
- Другие форматы (`xlsx`, `pptx`, `txt`, изображения отдельно).
- Пакетная обработка множества файлов.

## 4. Развертывание и приватность

Приложение — client-side: весь код исполняется в браузере пользователя, серверной части нет.

- Хостинг статический и бесплатный: GitHub Pages, Cloudflare Pages или Netlify. Хостинг отдает только код страницы, документы через него не проходят.
- Пользователь открывает приложение как обычную веб-страницу по ссылке. Устанавливать локально ничего не нужно.
- Документы не покидают компьютер: конвертация, OCR, детекция сущностей — всё считается прямо в браузере.
- Единственная сетевая активность — загрузка кода приложения и моделей (OCR, NER) при первом запуске. После кеширования приложение может работать и офлайн.
- Приложение не обращается к публичным LLM. Обезличенный текст пользователь загружает в облачную LLM уже вручную и осознанно.

Это самая приватная из возможных схем: данные буквально не выходят из вкладки.

## 5. Функциональные требования по модулям

### Модуль A. Загрузка и определение типа файла

- Прием файлов через веб-интерфейс (drag-and-drop и выбор файла).
- Определение формата по содержимому, а не только по расширению.
- Для PDF — определение, текстовый это документ или скан (проверка: есть ли извлекаемый текстовый слой). От этого зависит, нужен ли OCR.
- Если пользователь загрузил `.doc` — понятное сообщение с просьбой сохранить файл как `.docx`.

### Модуль B. Конвертация в Markdown

- `docx` → Markdown: через mammoth.js (docx → HTML) и turndown (HTML → Markdown). Сохранять заголовки, списки, таблицы, жирный/курсив.
- PDF с текстовым слоем → Markdown: через pdf.js (извлечение текста) с последующей сборкой в Markdown.
- PDF-скан → OCR → Markdown (модуль C).
- Таблицы в договорах важны — стараться сохранять их структуру.
- Результат — валидный Markdown в кодировке UTF-8.

Требование к качеству: заголовки, нумерация пунктов договора и таблицы не должны разрушаться. Это критично для юридического текста.

### Модуль C. OCR (для PDF-сканов)

- Распознавание английского текста со сканов через Tesseract.js (WASM, работает в браузере).
- Сохранение порядка чтения и по возможности структуры.
- Модель языка скачивается при первом запуске и кешируется.
- OCR выполняется в фоновом потоке (Web Worker), чтобы не подвешивать интерфейс.
- Индикатор прогресса — OCR медленнее прямой конвертации.
- Ограничение: на грязных или перекошенных сканах качество ниже, чем у серверных VLM-движков. Пользователь правит результат вручную (модуль E).

### Модуль D. Анонимизация (детекция сущностей)

Автоматическое обнаружение и замена по двум механизмам.

Структурные данные — через регулярные выражения (высокая точность):
- IBAN (с проверкой контрольной суммы mod-97).
- SWIFT/BIC.
- Номера банковских счетов.
- Номера карт (проверка по алгоритму Луна).
- Email.
- Телефоны.

Неструктурные данные — через браузерную NER-модель:
- ФИО физических лиц.
- Названия компаний (юридические лица).
- Адреса.

Регистрационные номера компаний и налоговые идентификаторы — через регулярные выражения под конкретные форматы.

Механика замены:
- Каждая найденная сущность заменяется на плейсхолдер с типом и номером: `[COMPANY_1]`, `[PERSON_1]`, `[IBAN_1]` и так далее.
- Одинаковые вхождения одной сущности получают один и тот же плейсхолдер (если `Acme Ltd` встречается 10 раз, везде будет `[COMPANY_1]`).
- Каждая замена фиксируется в таблице замен (см. модуль F).

Требования к качеству детекции:
- Приоритет на полноту (recall) — лучше показать пользователю лишнее и дать убрать, чем пропустить реальные данные.
- Пользователь всегда видит, что именно распозналось, и контролирует финальный результат вручную (модуль E). Ручной контроль компенсирует более слабое автоопределение имен и компаний в браузере.

### Модуль E. Редактор и ручное управление сущностями

- Двухпанельный или совмещенный вид: слева/сверху — текст, справа/снизу — список найденных сущностей.
- Найденные сущности подсвечиваются в тексте. По наведению видно оригинальное значение.
- Пользователь может:
  - Отключить анонимизацию конкретной сущности (вернуть оригинальный текст).
  - Добавить новую сущность вручную — выделить фрагмент текста и назначить ему тип и плейсхолдер.
  - Изменить категорию сущности (например, приложение сочло текст компанией, а это адрес).
  - Отредактировать сам Markdown-текст (исправить ошибки конвертации или OCR).
- Изменения в списке сущностей сразу отражаются в тексте, и наоборот.
- Предпросмотр «до/после» рядом — опционально, на будущее. На старте подсветки с показом оригинала по наведению достаточно.

### Модуль F. Таблица замен

- Таблица связывает плейсхолдер с оригинальным значением и типом.
- Основной вид — интерактивная таблица прямо в интерфейсе. Пользователь наглядно видит, какие сущности и на что заменились.
- Столбцы: плейсхолдер, тип сущности, оригинальное значение, количество вхождений.
- Экспорт для пользователя — в `csv` (открывается в Excel).
- Таблица — основа обратимости: по ней восстанавливается оригинал.

### Модуль G. Экспорт и деанонимизация

- Экспорт анонимизированного Markdown (`.md`).
- Экспорт таблицы замен (`.csv`).
- Обратная операция: приложение возвращает оригинал (замена плейсхолдеров на оригинальные значения) по сохраненной таблице замен.

### Модуль H. История обработанных документов

- Приложение хранит историю в браузере (IndexedDB).
- По каждому документу: имя, дата обработки, статус, результат (Markdown), таблица замен.
- Пользователь возвращается к любому документу из истории, смотрит результат и таблицу замен, повторно экспортирует.
- История привязана к браузеру и машине. Чтобы не потерять её при очистке браузера или переезде на другой компьютер, приложение дает экспорт и импорт всей истории отдельным файлом.

## 6. Рекомендуемая техническая архитектура

Всё client-side, стек на JavaScript/TypeScript.

**Каркас: React + Vite.** Сборка в статические файлы, разворачивается на бесплатном статическом хостинге.

**Конвертация документов:**
- `docx` → mammoth.js (в HTML) → turndown (в Markdown).
- Текстовый PDF → pdf.js (извлечение текста) → сборка в Markdown.

**OCR:** Tesseract.js (WASM-порт Tesseract), английская языковая модель, запуск в Web Worker.

**Анонимизация:**
- Структурные сущности (IBAN, SWIFT, счета, карты, email, телефон, рег. номера) — регулярные выражения с проверкой контрольных сумм, где они есть (mod-97 для IBAN, алгоритм Луна для карт). Это точнее и быстрее NER, модель тут не нужна.
- Неструктурные сущности (имена, компании, адреса) — GLiNER через библиотеку GLiNER.js (npm-пакет `gliner`) или более свежий форк `@lmoe/gliner-onnx`. GLiNER — zero-shot NER: типы сущностей (`"person"`, `"company"`, `"address"`, `"registration number"`) задаются во время запроса, что для юридического текста точнее фиксированных типов классических моделей. Модель — компактная квантизованная ONNX-версия (например, `onnx-community/gliner_small-v2.1` или PII-версия). Запуск в Web Worker.
- Запасной, более простой вариант для первого прототипа — `Xenova/bert-base-NER` через transformers.js (`@huggingface/transformers`). Работает из коробки, но типы грубее (PER/ORG/LOC/MISC) и регистрационные номера не ловит.
- GLiNER нельзя запустить через стандартный pipeline transformers.js — нужна именно GLiNER.js или ONNX-форк.
- Слой поверх детекции — нумерация плейсхолдеров (`[COMPANY_1]` и т. д.), дедупликация одинаковых сущностей, ведение таблицы замен.

**Редактор:** CodeMirror или markdown-редактор с наложением подсветки сущностей.

**Хранилище:** IndexedDB через обертку (Dexie.js или localForage). Хранит историю, результаты и таблицы замен. Плюс экспорт/импорт всей истории файлом.

**Фоновые вычисления:** OCR и NER — в Web Workers, чтобы интерфейс не подвисал на тяжелых документах.

**Хостинг:** GitHub Pages, Cloudflare Pages или Netlify (бесплатно).

## 7. Модель данных

Основные сущности:

- **Document** — обработанный файл: идентификатор, исходное имя, формат, дата обработки, статус, результат (Markdown), связанная таблица замен. Хранится в IndexedDB (история).
- **Entity** — найденная чувствительная сущность: идентификатор, тип (COMPANY/PERSON/IBAN/...), оригинальное значение, плейсхолдер, список позиций в тексте, флаг «анонимизировать/нет», признак «добавлена вручную».
- **ReplacementTable** — набор пар «плейсхолдер → оригинал» для документа.

## 8. Нефункциональные требования

- **Приватность** (раздел 4) — приоритет номер один. Данные не покидают браузер.
- **Прозрачность** — пользователь всегда видит, что и на что заменяется.
- **Контроль** — последнее слово по каждой замене за человеком.
- **Отзывчивость интерфейса** — тяжелые операции (OCR, NER) в Web Workers, с индикаторами прогресса.
- **Первый запуск** — модели OCR и NER скачиваются один раз и кешируются; далее приложение способно работать офлайн.
- **Расширяемость** — новые языки, форматы и типы сущностей добавляются без переписывания ядра.
- **Кодировка** — UTF-8 везде.

## 9. Этапы разработки

Разработку вести итеративно. Каждый этап дает работающий результат. Разрабатывать можно на любой машине (например, дома), готовые версии выкладывать на бесплатный статический хостинг.

**Этап 1 (MVP).** Каркас React + Vite на бесплатном статическом хостинге. Загрузка `docx` → конвертация в Markdown (mammoth + turndown) → показ результата → экспорт `.md`. Без PDF, без OCR, без анонимизации. Цель — проверить сквозной путь, развертывание и базовый интерфейс.

**Этап 2.** Добавить текстовый PDF (pdf.js). Тяжелые операции вынести в Web Worker.

**Этап 3.** Добавить OCR для PDF-сканов (Tesseract.js в Web Worker). Определение типа PDF и маршрутизация: текст напрямую, скан через OCR.

**Этап 4a.** Анонимизация структурных данных: регулярки для IBAN, SWIFT, счетов, карт, email, телефона, рег. номеров. Замена на плейсхолдеры, таблица замен в интерфейсе, экспорт в `csv`. Дает работающую анонимизацию без модели.

**Этап 4b.** Анонимизация неструктурных данных: GLiNER (GLiNER.js) для имен, компаний и адресов, запуск в Web Worker. Типы сущностей задаются под юридический текст.

**Этап 5.** Редактор: подсветка сущностей, включение/отключение, ручное добавление и удаление, правка текста.

**Этап 6.** История в IndexedDB плюс экспорт/импорт всей истории файлом.

**Этап 7.** Деанонимизация: восстановление оригинала по таблице замен.

**Этап 8. Офлайн-режим (PWA).** Service worker (например, через `vite-plugin-pwa` / Workbox), который прекеширует оболочку приложения (HTML/JS/CSS/WASM), чтобы после первого запуска приложение полноценно работало офлайн — как обещано в разделах 4 и 8. Модели OCR/NER кешируются в рантайме (Cache Storage / IndexedDB), статические ассеты — в precache. Опционально — web-манифест для установки как приложения. До этого этапа офлайн не гарантирован: кешируются только модели, но не код страницы.

**Этап 9. Качество конвертации PDF → Markdown.** Улучшить сборку Markdown из текстового слоя pdf.js: определять заголовки (по размеру/начертанию шрифта), списки и нумерацию пунктов, реконструировать таблицы (по координатам колонок), сохранять порядок чтения. Сейчас (этапы 2–3) текст из PDF склеивается плоско, без структуры, что нарушает требование Модуля B «заголовки, нумерация пунктов и таблицы не должны разрушаться». Для `docx` структура уже сохраняется.

**Этап 10 (будущее).** Нативная поддержка `.doc`, русский и другие языки, более точная NER, side-by-side предпросмотр «до/после».

## 10. Известные ограничения client-side подхода

- Старый `.doc` нативно не поддерживается — сначала пересохранить в `.docx`.
- Автоопределение имен и компаний слабее серверного Presidio; компенсируется ручной проверкой и высокой точностью регулярок на структурных данных.
- OCR на плохих сканах слабее серверных VLM-движков.
- История привязана к браузеру и машине; страховка — экспорт истории файлом.
- Первая загрузка моделей может быть небыстрой (потом кешируется).
- До этапа 8 полноценный офлайн не гарантирован: кешируются модели, но не оболочка приложения (нужен service worker).
- До этапа 9 Markdown из текстового PDF собирается плоско — без заголовков, списков и таблиц (для `docx` структура сохраняется).
