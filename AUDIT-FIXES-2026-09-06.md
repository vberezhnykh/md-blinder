## Производительность и архитектура

- Структурный поиск перенесён в отменяемый Worker. Квадратичный email-шаблон заменён линейным сканированием.
- Для PDF открывается один документ и создаётся один OCR Worker на все требующие OCR страницы. Рендер, canvas, PDF и OCR освобождаются при успехе, ошибке и отмене.
- Редактор и конвертеры загружаются по требованию. Начальный JS: **1 334,37 → около 259 КБ**, gzip **433,54 → около 82 КБ** (примерно −81%). Отложенные editor/PDF/model-ресурсы всё равно нужны при использовании соответствующей функции; это не уменьшение полного скачивания модели.
- История после сохранения читает только `documentMeta`, а полный документ загружается при открытии. Полное чтение остаётся для явного экспорта/импорта истории.
- Список сущностей использует заранее рассчитанные группы по типам; варианты объединения вычисляются для активной строки.
- GLiNER.js/Xenova и дублирующий ONNX Runtime удалены. Используются небольшой локальный span-адаптер, `@huggingface/tokenizers` и один ONNX Runtime Web. NER Worker уменьшился с примерно **2,06 МБ до 839 КБ**; отдельно поставляются согласованные JS/WASM-ресурсы (JSEP около 26,83 МБ и `.mjs` около 46,6 КБ), без второго неиспользуемого WASM-бандла.
- Модель fp16 и токенизатор закреплены на ревизии `6ddaeb9413b0e71ad8457da1aab378a165b24058`. При загрузке нет массива всех чанков с последующей полной конкатенацией и отдельной JS-копии ради Cache Storage; после инициализации адаптер не удерживает исходные modelBytes. Пиковая память браузера не измерялась: внутренний буфер кеша/ORT по-прежнему возможен.
- `useDocumentSession`, `useAnalysisJob`, `useHistoryStore` разделяют ревизии, отмену и надёжную запись. Для смешанных PDF усилена классификация и добавлен принудительный OCR всех страниц.

Синтетический `npm run test:perf`, Node 26.7.0, медиана 7 тёплых прогонов:

| Длина строки без email | Полный структурный поиск |
| --- | ---: |
| 8 000 | 0,10 мс |
| 16 000 | 0,16 мс |
| 32 000 | 0,26 мс |
| 64 000 | 0,50 мс |
| 256 000 | 2,01 мс |

На проблемной строке 64 000 символов исходный аудит измерил около 1,88 с. Новый экспорт с 2 000 заменами в этом микробенчмарке — 0,64 мс. Это локальные измерения отдельных функций, не обещание времени обработки произвольного документа. Совокупное ускорение OCR и потребление RAM не измерялись.

## Зависимости и ML-совместимость

Обновлены React 19.2.8, семейство CodeMirror 6, PDF.js 6.3.289, Mammoth 1.12.2, Vite 8.2.2, TypeScript 7.0.2, Vitest 5.0.0, Playwright 1.63.0 и сопутствующие инструменты. Node 24 LTS согласован в `.nvmrc`, CI и Netlify; npm закреплён на 11.19.0.

ONNX Runtime Web закреплён на **1.27.0**, а не на последнем 1.29.0. На одном и том же 10-текстовом CPU/WASM batch (один поток, та же fp16-модель) получено:

| Вариант | Инференс | Инициализация |
| --- | ---: | ---: |
| Старый runtime 1.19.2 | 27,47 с | 1,92 с |
| Проверенный 1.29.0 | 84,0 с | 2,27 с |
| Выбранный 1.27.0, CPU optimization `layout` | 26,07 с | 1,90 с |

Во всех 42 найденных фрагментах на 6 синтетических RU/UA/EN примерах и 4 локальных отложенных отрывках сохранены позиции и типы. Это ограниченная проверка совместимости, **не полный прогон отложенного корпуса и не доказательство неизменности recall для любых документов**. Время измерено одним сравнительным прогоном; небольшое преимущество 1.27 не объявляется гарантированным ускорением. Для 1.27 CPU исключён несовместимый fusion посредством поддерживаемой настройки `graphOptimizationLevel: 'layout'`.

У upstream есть отдельный отчёт о регрессии FP16 CPU в 1.29 на Windows native runtime. Его связь с нашим WASM-измерением — гипотеза, а основание выбора версии здесь — собственное сравнение. [ONNX Runtime issue #32255](https://github.com/microsoft/onnxruntime/issues/32255).

В реальном production Worker также проверен WebGPU на Intel gen12lp. Новый native-WebGPU путь ORT дал только 4 из 6 ожидаемых синтетических сущностей, поэтому выбран проверенный JS-WebGPU/JSEP backend через `/all`: он дал 6/6 без переключения приложения на WASM. Это не означает, что каждый отдельный узел модели выполняется на GPU — для такого вывода нужен profiling. Это осознанный выбор корректности: Worker около 839 КБ вместо 105 КБ у более компактного, но не прошедшего проверку native-backend. Сравнения со старым WebGPU на этой карте не проводилось; нельзя называть расхождение native-GPU/CPU доказанной регрессией старого GPU-пути.

Прогрев проверяет шесть известных RU/UA/EN сущностей. Если GPU не проходит эту самопроверку, его сессия освобождается и приложение пробует CPU; если и CPU не проходит, NER сообщает ошибку, а не успешную пустую детекцию. Такая самопроверка ловит грубые несовместимости backend, но не доказывает качество на произвольном тексте.

`npm audit` после обновлений: **0 известных уязвимостей** вместо исходных 11 записей. Это проверка базы advisory на дату запуска, а не гарантия отсутствия ошибок/уязвимостей в приложении. `npm audit fix --force` не применялся.

- `npm run test:e2e`: **12/12 Chromium-сценариев — успешно**, последний полный прогон 8,7 с. Реальны React, CodeMirror, IndexedDB, структурный Worker, clipboard и download. NER в этих гонках намеренно детерминированный.
- CI теперь включает `npm ci`, lint, unit и build на Windows/Linux; Chromium и advisory-проверку на Linux. Удалён обход через `npm install`. Конфигурация подготовлена локально; удалённый GitHub Actions run не запускался.
- В отдельном чистом каталоге выполнен настоящий Windows `npm ci`: успешно, 147 пакетов; запущены нативные TypeScript/oxlint и проверены rolldown/Lightning CSS. В другом чистом каталоге Linux x64/glibc `npm ci --dry-run` выбрал корректные платформенные пакеты. Это проверка разрешения зависимостей, **не фактическое выполнение Linux-сборки**. Исходный lock-файл не изменился. Два ненужных postinstall-скрипта protobufjs/Tesseract не разрешались вручную; установка и проверки работают без них.
- Локальный scorer отдельно считает полное/частичное/отсутствующее покрытие **всех** literal gold value/variants/aliases по активным позициям; unanchored gold и старые captures без activation flags не маскируются как успешные. Дополнительно проверяются буквальные остатки в предпросмотре. Legacy entity score сохранён для сравнимости. Пример: два `Acme`, одна замена → прежний `HIT`, новый occurrence recall **50%**.
- Старые локальные E2E-seed скрипты обновлены для схемы IDB v2. Реальный корпус и captures остаются в игнорируемых локальных каталогах; в CI только синтетические данные.
- README приведён к текущим функциям и содержит предупреждения о нешифрованной истории, исходных данных в CSV/JSON, изображениях, первой загрузке около 580 МБ, offline-ограничениях, CPU fallback и ручной проверке результата.

Ограничения остаются явными: автоматическое обезличивание и OCR не дают стопроцентной гарантии; мобильные браузеры и вся матрица видеокарт не проверены. Большой редактор остаётся отдельным чанком около 613 КБ, поэтому Vite показывает предупреждение о размере отложенного чанка. Оно не скрыто повышением лимита.
